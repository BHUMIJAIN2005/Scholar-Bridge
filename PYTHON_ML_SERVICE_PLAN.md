## The Two Halves of This Service

**1. Offline — training (`train.py`, run once by you, not by the live app)**
This is a script you run yourself while developing, not an API endpoint. It reads a labeled dataset, trains the classifier, evaluates it, and saves the trained model to disk.

**2. Online — inference (`main.py`, the live API)**
This is what actually runs when the Java backend calls it. It loads the *already-trained* model from disk at startup and just uses it to make predictions — it does not retrain anything on each request.

Keeping these separate matters: training is slow and only needs to happen once (or occasionally, if you improve the model); inference needs to be fast, since a student is waiting on it after an upload.

## Step-by-Step Build Plan

### Week 1 — Get a labeled dataset
1. You need text samples labeled with a category (Machine Learning, Web/Cloud Systems, Cybersecurity, DSA, IoT, etc.) to train on.
2. The easiest source: **arXiv's public dataset** of paper abstracts and their subject categories (searchable on Kaggle and arXiv's own API) — filter it down to CS-relevant categories and a manageable sample size (a few hundred to a couple thousand rows is plenty for a prototype).
3. Map arXiv's category codes to your five-or-so simplified categories (e.g. `cs.LG`, `cs.CV`, `cs.CL` → "Machine Learning"; `cs.CR` → "Cybersecurity"; `cs.DC`, `cs.NI` → "Web/Cloud Systems").
4. Save the result as `data/training_abstracts.csv` with two columns: `text`, `category`.

### Week 2 — Preprocessing & training script
1. Write `utils/preprocess.py` — lowercase, strip punctuation/stopwords. Keep this simple; heavy preprocessing usually isn't necessary for TF-IDF to work reasonably well.
2. Write `model/train.py`:
   - Load the CSV.
   - Split into train/test sets (e.g. 80/20) — **do not skip this**, it's what lets you report real accuracy numbers.
   - Fit a `TfidfVectorizer` on the training text.
   - Train a classifier (`MultinomialNB` is a good first choice — simple, fast, works well on text) on the vectorized training data.
   - Evaluate on the held-out test set: print accuracy, and a `classification_report` (precision/recall/F1 per category) and a confusion matrix. **Save these outputs** — this is your evaluation section for the project report.
   - Save the fitted vectorizer and classifier with `joblib.dump(...)`.
3. Run this script once. If accuracy looks poor, try `LogisticRegression` instead of Naive Bayes, or adjust the category mapping — a bit of iteration here is normal and expected.

### Week 3 — PDF extraction & the live API
1. Write `utils/pdf_extract.py` using `pdfplumber` — given a file, return the extracted text (concatenate all pages, or just the first page/abstract if you want to keep it fast).
2. Write `main.py`:
   - On startup, load `classifier.joblib` and `vectorizer.joblib` into memory.
   - Define `POST /categorize`, accepting either a raw text string or a PDF file upload (see contract below — decide which side does extraction based on what's simpler for your Java integration).
   - Preprocess the input text the same way training data was preprocessed, vectorize it with the *already-fitted* vectorizer, run `classifier.predict()` and `classifier.predict_proba()` to get both the category and a confidence score.
   - Return `{ "category": "...", "confidence": 0.87 }`.
3. Run the service locally (`uvicorn main:app --reload`) and test it directly in Postman with a few sample PDFs or raw text, before touching the Java side at all.

### Week 4 — Polish & integration handoff
1. Add basic error handling — if extraction fails (corrupted PDF, empty file), return a clear error response rather than a 500 crash.
2. Confirm the request/response shape matches exactly what's documented in `ARCHITECTURE_AND_ROLES.md`'s communication contract — this is the one thing that must line up with the Java side.
3. Hand off to `BACKEND_PLAN.md` Week 5 for wiring this into the main system.

## Deciding: does Java or Python extract PDF text?

Two valid options — pick one and be consistent:

- **Option A (recommended, simpler):** Java saves the raw PDF file and sends it to Python as a multipart upload; Python does the extraction itself using `pdfplumber`. Python owns the entire "understand this document" job, which keeps the split clean.
- **Option B:** Java extracts text first (using Apache PDFBox) and sends plain text to Python. This avoids sending large files over the internal network, but means Java needs a PDF-parsing dependency too, slightly blurring the split.

Either is defensible — Option A keeps the architectural story cleaner for your viva ("Python handles everything about reading the document"), so default to that unless you have a specific reason not to.

## What to put in your project report from this service

This is your strongest "research" evidence — make sure you keep, and write up:
- The size and source of your training dataset
- The train/test split
- The accuracy, precision, recall, and F1-score per category
- The confusion matrix (which categories get confused with which — e.g. Machine Learning vs Data Science content often overlaps, and that's a genuinely interesting thing to discuss)
- A brief note on the baseline you'd compare against if you have time (e.g. a simple keyword-count heuristic vs your trained classifier) — even a short comparison table makes the "research" framing much stronger
